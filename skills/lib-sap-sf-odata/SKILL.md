# Документация SAP SuccessFactors OData V2

Подтверждай сведения через read-only MCP `lib-docs`. Работай только с библиотекой `sap-sf-odata` и не расширяй область без указания пользователя.

## Определить область

- До любого вызова инструмента проверь предметный текст пользователя. Не считай путь к этому `SKILL.md`, загрузку навыка или служебную инструкцию прочитать его явным указанием продукта.
- Явное название SAP SuccessFactors, SuccessFactor(s), SF OData, `$lib-sap-sf-odata` или техническое имя `sap-sf-odata` однозначно задаёт библиотеку.
- Название сущности или операции однозначно только тогда, когда оно специфично для SuccessFactors API.
- Если в предметном тексте нет явного названия из предыдущего пункта или уникальной сущности SuccessFactors, выбор библиотеки не достиг 100% определённости. Для общего `OData`, `SAP OData`, `upsert`, `batch` или других пересекающихся терминов задай ровно один короткий уточняющий вопрос. Выведи только вопрос. До ответа не вызывай инструменты, не делай предположение о SuccessFactors, не формируй разделы и footer. Это правило имеет приоритет над поиском.
- Если пользователь явно ограничил поиск этой библиотекой, сохрани границу. Непокрытую часть отметь отдельно; не подменяй её сведениями из другого SAP API.
- Никогда не вызывай `find_version`, `search_docs`, `fetch_url` или `list_libraries` для другой библиотеки. Если весь запрос вне области SuccessFactors OData V2, не вызывай инструменты и оформи непокрытый пункт.
- Библиотека покрывает SuccessFactors OData V2. OData V4, SAP Gateway, S/4HANA, ByDesign и другие SAP API находятся вне области.

## Найти подтверждение

1. Если указан релиз, нормализуй четырёхзначную метку до версии индекса, добавив `.0.0`, затем первым вызови `find_version` с `library="sap-sf-odata"`. Если найденная версия не соответствует запрошенному релизу, остановись до `search_docs`, оформи несовместимость и запроси разрешение использовать найденную версию. Во всех поисках передавай найденную версию. Без релиза используй доступную версию библиотеки без выдуманного ограничения.
2. Сформулируй один начальный запрос ключевыми терминами SAP: точными именами всех нужных сущностей, свойств, navigation properties, операций, HTTP-методов, параметров, разрешений, ошибок и аспектов составного вопроса.
3. Первый и единственный начальный `search_docs` выполни с `limit=5`. Изучи все пять результатов до следующего вызова.
4. Если подтверждение неполное, уточни запрос не более двух раз. Абсолютный предел на весь пользовательский запрос — три `search_docs` в библиотеке `sap-sf-odata`, а не три на каждый пункт. После третьего поиска остановись. Для повторов используй только `limit=5` или `limit=10`; `limit=10` допустим лишь после оценки первого результата.
5. `fetch_url` вызывай только для URL из результата, когда фрагмент обрывает таблицу, payload или условие. Не используй его как дополнительный поиск.
6. При ошибке доступности один раз вызови `list_libraries`. Не подменяй отсутствующую библиотеку или версию другой.

Первоисточник — SAP SuccessFactors API Reference Guide for OData V2 под `https://help.sap.com/docs/successfactors-platform/sap-successfactors-api-reference-guide-odata-v2`. Каждый существенный вывод должен опираться на найденный фрагмент или открытую страницу. Если основания нет, прямо напиши, что подтверждение в выбранной документации не найдено.

## Сформировать ответ

1. Начни с прямого вывода в 1–3 предложениях без заголовка.
2. Добавь точный заголовок `## По документации`.
3. Оформи все подтверждённые и непокрытые положения последовательными пунктами `### 1.`, `### 2.` и далее только внутри этого раздела. Не создавай отдельный раздел для непокрытой части и не смешивай её с подтверждённым пунктом.
4. После текста каждого подтверждённого пункта оставь пустую строку и отдельную строку источника:
   `[Источник] {Название официальной документации}; {Раздел}; <{публичный URL}>`
5. В одном подтверждённом пункте литерал `[Источник]` используй ровно один раз — только в начале строки источника. Никогда не повторяй `[Источник]` после `|`. Несколько источников перечисляй в той же строке через ` | `; каждый фрагмент по обе стороны разделителя обязан быть полным источником с собственными названием документации, разделом и, если подтверждён, публичным URL. Не ставь после `|` отдельный URL или раздел. Строка содержит только эти поля. Если библиотека вернула только внутренний путь, не показывай `file://`, не выдумывай URL и закончи источник после раздела без поясняющей фразы.
6. Если нужен синтез, добавь `## Выводы и рекомендации` с нумерованными рекомендациями, основанными только на подтверждённых пунктах.
7. Последней строкой без текста после неё выведи `[Использованы библиотеки: sap-sf-odata]`, если `search_docs` был вызван хотя бы один раз. Если поиск не вызывался из-за неоднозначности, неподдерживаемой области или несовместимой версии, используй `[Использованы библиотеки: нет]`; при одном уточняющем вопросе до поиска footer не добавляй.

Даже при недоступности MCP, отсутствии версии или подтверждения сохраняй эту структуру: помести состояние в `### 1.`, не добавляй выдуманный `[Источник]` и заверши точным footer.

Не показывай даты снимков, `Snapshot date`, `undefined`, внутренние пути и сырые ответы MCP. Сохраняй точные имена сущностей, свойств, операций, HTTP-методов, параметров, кодов ошибок и разрешений.
