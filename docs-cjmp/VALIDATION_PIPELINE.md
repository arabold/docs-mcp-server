# CJ-UI 文档检索优化 · 验证报告

> 本文回答一个问题：**我们改了 MCP 文档检索，怎么证明改得有效？**
> 写法约定：术语第一次出现时都会解释；每个数字都注明它是从哪测出来的。
> 配套文件：`PYRAMID_RETRIEVAL_SPEC.md`（改动方案设计）、`eval/`（测试题库与全部原始数据）。

## 术语表（先读这个，后文不再重复解释）

| 术语 | 含义 |
|---|---|
| MCP 检索服务 | docs-mcp-server。agent 写代码时用它按关键词查文档，相当于"帮 agent 查 API 手册"的工具 |
| 金字塔文档 | 我们自己编写的 CJ-UI 文档库，分三层：L1 总索引（1 篇）、L2 按场景的案例教程（10 篇）、L3 单个 API 明细（254 篇） |
| 召回率 | 衡量"查得准不准"：发 100 条查询，有多少条把正确文档带回来了。下文"真实查询召回"指只用手工写的、贴近实际用法的查询来算（自动生成的查询偏简单，分数会虚高） |
| 返回量 | 衡量"查得贵不贵"：一次查询返回多少字符。返回越多，占 agent 上下文越多、消耗 token 越多 |
| 运行日志 | 每次任务的完整运行记录（`bench-run/opencode.stdout.jsonl`），记录 agent 每一步调了什么工具、发了什么查询、返回了什么内容 |
| 对照实验 | 每次只改一个变量、其余不动，对比两组结果——用来确定每个改动各自的贡献 |
| 四个文档实验组 | 金字塔组＝只加载金字塔文档（不用 MCP）；原版 MCP 组；纯官方 MCP 组（原版 MCP，只索引官方文档）；**优化组＝本文的改进版 MCP**。其他报告里的"臂1/臂2/臂2b/优化臂"即依次对应这四组 |
| 裸奔组（反事实组） | 什么都不给：不加载任何语言文档、不用 MCP，只留 3 个纯工具链 skill（keels 命令用法、项目模板、界面测试流程）。用来回答"如果完全没有文档通道会怎样" |
| judge 评分 | 自动评分器（Qwen3.7-Plus 模型）对任务完成度打分，满分 100 |
| 单次运行 | 每个任务每个配置只跑一遍，没有重复多次取平均。同一任务重跑的分数波动可达 ±28%，所以端到端的小差距不可靠 |
| token | 模型的计费和上下文单位。一个任务的 token 总消耗 ≈ 对话轮数 × 每轮上下文大小，其中约 92% 是反复读取已累积的上下文（缓存读） |

## 0. 先说结论

| 在哪个层面验证 | 结论 | 关键数字 | 可信度 |
|---|---|---|---|
| 检索工具本身（离线出题测试） | 两项改动各自有效：文档拆分治好"查不到"，摘要卡片治好"一次拖回太多" | 真实查询召回 28.1%→81.3%；单次返回量 6758→3822 字符（-43%，且有硬顶 4.2K） | 高（114 道题、变量隔离） |
| agent 实际使用（线上日志） | agent 正常用新工具，返回量可控且有硬顶 | 同条件实测：单次返回中位 6806→3404（-50%）、P90 18582→4335（-77%）、最坏 21620→4784 | 中 |
| 反事实对照（裸奔组） | **把文档通道整个拿掉，平均分掉 6.6 分，token 反而没省**——文档＋检索通道的价值在分数，且代价极小 | 优化组 83.9 分/均 6.52M token vs 裸奔组 77.3 分/均 6.75M token | 中（单次运行，7 任务方向一致） |
| 任务端到端（bench 全流程） | **检索不是 token 总消耗的主要来源，优化检索省不动总账** | 检索返回量只占总消耗 0.26%；重迭代任务一项占总额约 47% | 低（单次运行），且是否定性的 |

**本文的核心论点**（一句话）：改进后的 MCP 检索是真实有效的——查得更准（召回 28%→81%）、返回更省（线上单次 -76%）、拿掉它分数就掉（83.9→77.3）；**但任务的 token 总消耗大头从来不在检索**（只占 0.26%，真正的变量是"来回修改多少轮"），所以改进 MCP 之后总 token 没有明显下降——这不表示 MCP 没用，只表示 token 的治理杠杆在别处。

## 1. 验证思路（七步）

1. **看日志**：agent 实际怎么查文档——用什么语言、查多少次、每次返回多大；
2. **找问题**：原版 MCP 差在哪；
3. **做改动**：两项改动，一项治"查不到"，一项治"返回太多"；
4. **出题**：构造 114 道检索测试题，每题有标准答案；
5. **做对照**：五组配置对比，把效果分别归因到两项改动；
6. **回到真实任务**跑一遍，并如实清点这套验证还有哪些不可信的地方；
7. **反事实验证**：把文档通道整个拿掉再跑一遍（裸奔组），直接称出文档＋检索通道的价值。

写作纪律：所有数字注明测量来源——"日志实测"、"离线出题测试"、"评分器打分"、"逐轮重算"——不同来源的数字不混用。

## 2. 第一步：看日志——agent 实际怎么查文档

从 7 个任务的运行日志里提取全部文档查询记录。优化组共 109 次调用：45 次关键词查询（search_docs）＋ 64 次点名读取章节（read_section）。

| 任务 | 查询次数 | 点名读取次数 |
|---|---|---|
| calculator | 7 | 6 |
| entry-threshold-task | 3 | 7 |
| flashcard-quiz | 6 | 6 |
| meituan-prototype | 12 | 22 |
| menu-interaction | 7 | 4 |
| rider-plan-hub | 4 | 6 |
| shopping-cart | 6 | 13 |

**发现一：agent 全部用英文 API 名查文档，一条中文都没有。** 45 条查询全部形如：

```
"Grid GridItem layout columns rows"
"padding margin border EdgeMargin EdgePadding object literal syntax"
```

虽然任务说明、文档正文都是中文，agent 查文档时用的却是组件和 API 的英文名。这一点很关键：线上环境没有向量检索（代理服务器只有对话模型，没有 embedding 模型），检索完全靠关键词匹配（BM25），而"英文 API 名关键词"恰好是关键词匹配最擅长的形式。**所以测试题库必须用同样的形式出题**（见第四步），否则测出来的成绩不代表真实使用。

**发现二：查询频率不高。** 每个任务查 3~12 次，优化空间在"每次返回多少"，不在"查多少次"。

**原版 MCP 的日志实测（作为对比基准）**：34 次查询，单次返回量中位数 14200 字符，最大 34800——经常整篇教程全文拖回来。

## 3. 第二步：原版 MCP 差在哪

两个结构性问题：

1. **整本文档挤在一个地址下**。金字塔文档被索引成一个 3MB 的单页，1732 个片段共用一个地址。关键词命中后，系统按"命中段落＋前后相邻段落"拼一大块返回，没法只取想要的那一节。
2. **只有全文一档，没有摘要**。agent 只需要"这个组件有哪些参数"，却被迫收下整篇教程。

离线出题复核：原版对真实查询的召回只有 28.1%——不但贵，还查不准。

## 4. 第三步：两项改动

| 改动 | 内容 | 治什么 |
|---|---|---|
| 改动一：文档拆分 | 把金字塔拆成 265 个独立检索单元（1 篇总索引 ＋ 10 篇案例教程 ＋ 254 篇 API 明细），每篇有独立地址，开头附元信息（层级、主题、API 名清单） | 查不到 |
| 改动二：摘要卡片＋分层读取 | 查询默认只返回每篇的"摘要卡片"（章节目录＋函数签名清单，几百字符）；agent 看中哪篇，再用 read_section 点名读取那一节或全文 | 返回太多 |

工作方式（与金字塔三层结构一一对应）：

```
关键词查询 ──► 摘要卡片（每篇几百字符：列章节和函数名）
               │ 大多数情况看卡片就能写代码
               ▼ 需要细节时点名要
read_section ──► 指定章节全文（1~3K 字符）
               ▼ 需要整篇时
read_section ──► 整篇文档
```

设计原则一句话：**agent 上下文里的每个字符都是它点名要的，没有顺带塞进来的。**

## 5. 第四步：出题——114 道检索测试题

每道题 ＝ 一条查询 ＋ 标准答案（应该返回哪篇文档的哪个章节）。

- **32 道手写题**：刻意模仿第一步日志里看到的真实查询形式（英文 API 名关键词），如 `"Grid GridItem layout grid columns rows"`；
- **82 道自动生成题**：从文档元信息里把 API 名拼成查询。这类题自带答案关键词、偏简单，统计时和手写题分开算，**以手写题的数字为准**；
- **8 道中文题**：防备将来 agent 改用中文提问的底线覆盖。

判分规则（新旧版本都适用）：返回结果的地址包含标准答案的文件路径，或内容包含答案章节的标题／标记，算命中。

指标两个：**召回率**（查得准不准）和**单次返回字符数**（查得贵不贵）。

如实说明一处条件不对等：旧版测试时每次返回 3 条结果，新版定稿是 5 条。但新版返回条数更多反而便宜十倍，这个偏差对结论有利。

## 6. 第五步：对照实验（五组）

| 组 | 配置 | 包含哪些改动 | 召回率（总） | 召回率（手写题） | 单次返回中位字符 |
|---|---|---|---|---|---|
| 1 | 原版 MCP | 无 | 63.2% | 28.1% | 6758 |
| 2 | 只做文档拆分 | 改动一 | 93.9% | 78.1% | 5429 |
| 3 | 拆分，正式库（含另外 4 个文档库同场竞争） | 改动一 | 91.2% | 68.8% | 5420 |
| 4 | 拆分＋卡片，每次返回 3 条 | 改动一＋二 | 89.5% | 62.5% | 2230 |
| 5 | **拆分＋卡片，每次返回 5 条（定稿）** | 改动一＋二 | **94.7%** | **81.3%** | **3822** |

怎么读这张表：

- **召回率的提升来自文档拆分**：第 1→2 组只做了拆分，真实查询召回就从 28.1% 升到 78.1%；
- **返回量的下降来自摘要卡片**：第 2→5 组只差"卡片"这一项，返回量从 5429 降到 3822 字符（-30%），且最大值从 1 万级压到 4219 的硬顶；
- **卡片会让召回略降**（第 4 组手写题 62.5%），因为摘要比全文难匹配；把每次返回从 3 条提到 5 条、并让同一篇文档只占一个名额后，召回回到 81.3%——这就是定稿"卡片＋返回 5 条"的原因。

**勘误记录（2026-09-03）**：本表早先报告的"卡片负载 405/672 字符"是测量 bug——脚本对卡片模式的结果只累加了 `content` 字段，而卡片正文实际在 `card` 字段，`content` 为空，因此只量到了网址长度。修复后上表为真实值（每张卡片正文 500~700 字符，5 张合计中位 3822）。原"负载降 90%"的说法作废，真实降幅见上表；线上实测（下一节，直接量 agent 收到的完整文本，不受此 bug 影响）中位 3404 可与本表交叉印证。

## 7. 第六步：放回真实任务验证

条件：7 个界面开发任务（ui-interaction），Android 模拟器，新版执行规则（界面测试一次全过就冻结、编译错误攒一批再修），judge 自动评分，每个任务跑一次。

### 7.1 检索工具在线上的实际表现（日志实测）

**同条件对照**（2026-09-01/02，同为 Android 模拟器、同一执行规则、同一模型，从运行日志逐次实测）：

| 指标 | 原版 MCP（臂2 重测，18 次查询） | 改进版（优化组，45 次查询） | 变化 |
|---|---|---|---|
| 单次查询返回量（中位） | 6806 字符 | 3404 | **-50%** |
| 单次查询返回量（P90） | 18582 | 4335 | **-77%** |
| 单次查询返回量（最坏） | 21620 | 4784 | **-78%** |
| 返回量分布 | 方差极大：同组各任务中位 3.4K~21.6K 不等，取决于命中多大的文档块，agent 无法控制 | 硬顶在 4.8K 以内，可预测 | 有硬顶 |

原版返回多少字符是"撞大运"——查询碰中整篇教程就拖回两万字符；改进版有结构性上限。对 agent 的上下文预算而言，"最坏不超过多少"比"平均多少"更重要。

另两个观察：① 原版组 calculator 任务一次查询都没发（agent 没用文档也做出来了），7 个任务里 5 个用到了检索；改进版 7 个任务全部用检索（45 次），说明卡片式返回门槛低、agent 更愿意查；② 最早（8 月底，iOS/旧规则条件下）测得的原版数字是中位 14200、最坏 34800（34 次查询，旧轨迹已清理，为当时记录值），比同条件复测更重，原因是旧规则下查询词更宽泛——两组数字都保留，同条件复测为准。

| 汇总指标 | 8 月原测（旧条件，参考） | 同条件复测（为准） |
|---|---|---|
| 原版中位 / 最坏 | 14200 / 34800 | 6806 / 21620 |
| 改进版中位 / 最坏 | — | 3404 / 4784 |

改进组全程 45 次查询＋64 次点名读取的总注入约 42 万字符（≈12 万 token），占七任务总消耗 4561 万 token 的 **0.26%**。

### 7.2 离线 3822 与线上 3404 的口径差

两个数字测的是同一协议，量的是不同的"包裹"：离线只累加卡片正文与网址（3822）；线上是 agent 实际收到的完整工具返回（3404，中位），含卡片间的编号、路径与"如何读取全文"提示语，但中位反而略低——因为线上 45 次查询里有一部分命中少于 5 张卡。两侧互为印证：量级一致（3.4K~3.8K）、硬顶一致（4.2K~4.8K），说明"卡片协议"在线上没有走样。另有一个已记录待修的小毛病：部分卡片的摘要里混进了索引系统的元信息头（界面上显示成 undefined 字样），不影响判分。

### 7.3 端到端成绩

| 维度 | 改进版 | 原版 MCP | 目标 | 达成 |
|---|---|---|---|---|
| judge 平均分 | 83.9 | 84.4 | ≥82.4 | 达标（差 0.5 在单次运行的噪声范围内） |
| token 均值（逐轮重算） | 652 万 | 410 万（metadata 口径，偏低） | ≤287 万 / ≤205 万 | **未达标** |

原版 MCP 组的 410 万是系统自带统计（在会话接续场景漏记，最多低报 8 倍），与改进版的逐轮重算口径**不可直接比大小**；同口径的干净对比见第 8 节（优化组 652 万 vs 裸奔组 675 万）。token 目标未达的机理也在第 8 节展开：总 token 由轮数×上下文决定，检索只占 0.26%。

任务层面还有一个直接证据：**美团原型任务来回修改了 519 轮**（是计算器任务的 5 倍），一项占掉七任务总额的一半——它的 token 大头是"反复改界面"，检索优化管不到那里。

## 8. 第七步：反事实验证——把文档通道整个拿掉（裸奔组）

**设置**：与优化组完全同条件——同 7 个任务、Android 模拟器、同一套执行规则、同一评分器、同一模型；唯一差别是**不给任何语言文档、不给 MCP**（只留 keels 命令用法、项目模板、界面测试 3 个纯工具链 skill），并把 AGENTS.md 里所有"查文档"的指引替换为"以编译器为唯一事实源"。

**逐任务成绩**（token 均为运行日志逐轮重算口径）：

| 任务 | 优化组 分数 | 优化组 token | 优化组 轮数 | 裸奔组 分数 | 裸奔组 token | 裸奔组 轮数 |
|---|---|---|---|---|---|---|
| calculator | 96 | 4.67M | 105 | 84 | 3.67M | 87 |
| entry-threshold-task | 97 | 2.51M | 61 | 92 | 4.28M | 113 |
| flashcard-quiz | 88 | 3.92M | 85 | 80 | 4.26M | 97 |
| meituan-prototype | 49 | 23.32M | 519 | 40 | 21.90M | 488 |
| menu-interaction | 73 | 3.42M | 82 | 75 | 2.49M | 50 |
| rider-plan-hub | 94 | 3.94M | 95 | 88 | 7.21M | 175 |
| shopping-cart | 90 | 3.84M | 93 | 82 | 3.43M | 83 |
| **平均 / 合计** | **83.9** | **均 6.52M** | 1040 | **77.3** | **均 6.75M** | 1093 |

### 8.1 这张表怎么读

**读法一：文档＋检索通道买的是分数，6.6 分。** 裸奔组 7 个任务里 6 个低于优化组（menu-interaction 反超 2 分，在评分器噪声内）。拿掉文档，agent 只能靠"猜签名→编译报错→再猜"推进，画矢量图标这类没有先验可猜的任务（rider-plan-hub）掉得最明显。

**读法二：没有文档并不省 token——省下的检索开销被编译试错吃掉了。** 直觉上"不查文档=更省"，实测裸奔组 token 均值反而高 3.5%（6.75M vs 6.52M）。机制看得见：entry-threshold-task 轮数 61→113（+85%）、rider-plan-hub 95→175（+84%），全是编译试错循环顶替了文档查询；只有 calculator 这类模型本来就会写的简单任务，裸奔才更省（不用读任何东西）。**反过来说：优化组只多花 3.5% 的 token 就买到 6.6 分——文档通道是全场性价比最高的一笔开销。**

**读法三：总 token 由任务本身的迭代量决定，与有没有文档基本无关。** meituan-prototype 一项在两组里都占总额的 46%~49%（23.3M / 21.9M），轮数都在 490~520。这类重迭代任务的 token 大头是"反复改界面→反复截图对照"，检索（有或没有）都不是变量。

### 8.2 五组全景（含此前四组，供横向对照）

| 实验组 | 文档条件 | 平均分 | 平均 token | 备注 |
|---|---|---|---|---|
| 金字塔组（臂1） | 金字塔文档直接读 | 85.4 | 6.12M | token 为当时口径，设备 iOS |

## 9. 这套验证还有哪些不可信之处（如实清点）


1. **查询语言依赖当前模型的行为**：45/45 英文关键词查询是 GLM-5.2 现在的用法；换一个爱用中文提问的模型，关键词匹配对中文分词的表现没有测过（题库里只有 8 道中文题兜底）；
2. **离线测试没有 agent 参与**：只测工具本身，测不出"agent 会不会用好它"；
3. **端到端每个任务只跑了一次**：0.5 分的差距不做数（同任务重跑波动 ±28%）。裸奔组 6.6 分的差距虽也是单次运行，但 7 个任务里 6 个方向一致，可信度高于任何单任务数字；
4. **新旧版返回条数不齐**（3 条 vs 5 条），已在第五步声明；
5. **token 统计口径有过教训**：系统自带的统计在会话接续场景会漏记（最多漏 8 倍），本文所有 token 数字都是从运行日志逐轮重算的；
6. **评分器有抖动**：同一份产物两次评分能差 40 分，所以只看 7 个任务的平均分，不看单任务。

## 10. 结论

1. **工具层面（可信度高）**：两项改动各自有效、可分开验证——文档拆分把真实查询召回从 28.1% 提到 81.3%；摘要卡片把单次返回量降约一半（线上中位 6806→3404，-50%），且最坏情况被压在 4784 字符的硬顶（对 agent 的上下文预算来说，"最坏不超过多少"比"平均多少"更重要）；
2. **反事实层面（可信度中，方向一致）**：把文档通道整个拿掉，7 任务平均分 83.9→77.3（6/7 任务下降），而 token 不降反微升——**文档＋检索通道用约 3.5% 的 token 代价买到 6.6 分，是性价比最高的开销；它的价值在"做对"，不在"省字"**；
3. **token 层面（否定结论，回答"为什么改进后总 token 没降"）**：检索返回量只占任务总消耗 0.26%，总 token ≈ 轮数 × 上下文，由任务迭代量决定（meituan 一项在两组都占约 47%，有没有文档都一样）。所以改进 MCP 省不动总账——这不是 MCP 没用，是 token 的治理杠杆本来就在别处：管住来回轮数（执行规则、测试冻结）远比优化检索有效；
4. **使用层面（可信度中）**：agent 正常接受并使用新工具，"查摘要→点名读全文"的用法成立（45 次查询跟进 64 次点名读取）；
5. **方法层面**：这套七步流程（看日志→找问题→做改动→出题→对照实验→回到真实任务→反事实对照，外加清点局限）可以直接搬到任何"自有文档＋检索工具"的优化上。

## 11. 如何复现

**常设关卡（推荐入口）**：bench 里的 `mcp-api-judge/retrieval-gate` 任务（engine-eval 类型，不跑 agent、不需要设备、无需模型凭据，约 3~5 分钟），一条命令对同一份 114 题并排出三列——grep 直读（无 MCP 基线）／原版 MCP／当前 track 部署的 MCP：

```bash
python3 bench/runner/scripts/run_tasks.py --track cjmp --filter "mcp-api-judge/*" --agent opencode
# 结果 JSON（含逐题记录）: bench/tasks/mcp-api-judge/retrieval-gate/workspace/retrieval-gate/retrieval-gate.json
```

关卡自检：track 处于原版配置时，original 与 current 两列应完全一致（original 侧现为官方 arkui-cj 文档语料，"一致"仅在与 track 同语料时成立；常态下两列差值即 track 配置与"原版服务＋官方文档"基线的差距）。关卡题库 2026-09-03 瘦身为 **32 道手写题**（82 道自动生成题移除：题面自带答案关键词、召回虚高；fork 仓库 `docs-cjmp/eval/eval_set.jsonl` 保留 114 题全量作为历史实验记录）。瘦身后首测（track＝原版 bundle 配置，original＝官方文档语料）：grep 召回 78.1%／返回量中位 59,179 字符；原版服务＋官方文档 59.4%／17,562 字符；原版服务＋大书 bundle 34.4%／17,896 字符——**同一服务、仅换语料组织方式，召回差 25 个百分点**；fork 卡片（历史值 81.2%／3,822、硬顶 4,219）仍是唯一双优通道。

**手工复现各步**：

```bash
cd /Users/user/Desktop/project/docs-mcp-server

# ① 生成拆分后的文档语料（265 个检索单元，带元信息和摘要块）

import json, glob

    for line in open(f):

            p = ev['part']; print(p['tool'], p['state']['input'], len(p['state'].get('output','')))
EOF
```
