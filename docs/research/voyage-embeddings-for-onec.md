# Voyage Embeddings для русской документации 1С

Дата проверки: 9 августа 2026 года.

## Короткий вывод

Если выбирать замену текущему dense-режиму BGE-M3 по соотношению цены и
качества, первым кандидатом стоит тестировать **`voyage-4-lite`**. Он стоит
`$0.02 / 1M` токенов — вдвое дороже DeepInfra BGE-M3 (`$0.01 / 1M`), но для
аккаунта Voyage действует 200 млн бесплатных embedding-токенов. Полная
индексация нашего корпуса приблизительно из 6,1 млн токенов сейчас укладывается
в free tier; после его исчерпания она стоила бы около **$0.122**.

Окончательно заменять BGE-M3 только по публичным бенчмаркам нельзя: Voyage не
публикует русский результат серии 4, напрямую сопоставимый с русскими строками
MIRACL/MKQA для BGE-M3. Нужна одинаковая переиндексация и наш тест из 40
вопросов. Уже подтверждено лишь то, что текущий BGE-M3 + FTS5/RRF без reranker
даёт `MRR 0.684` и `nDCG@5 0.712`; это и есть контрольная точка.

Практические варианты:

1. **Без изменения кода:** `voyage-4-lite`, 1024 float, через существующий
   OpenAI-совместимый клиент. Это годится для технического smoke и сравнительного
   теста, но клиент не отправит рекомендуемый Voyage `input_type`, поэтому такой
   режим нельзя считать оптимальным production-вариантом.
2. **С небольшим adapter:** передавать `input_type=document` при индексации и
   `input_type=query` при поиске. Базовый кандидат остаётся
   `voyage-4-lite`. Дополнительный price/quality-вариант — индексировать документы
   через `voyage-4-large`, а дешёвые пользовательские запросы считать через
   `voyage-4-lite`: серия 4 использует общее совместимое пространство векторов.

С учётом уже доказанного большого эффекта `rerank-2.5-lite` приоритет остаётся
таким: сначала внедрить reranker, затем отдельным экспериментом сравнить
BGE-M3 и Voyage embeddings. Смена embedding требует полной переиндексации, а
reranker — нет.

## Что известно о качестве

Официальная таблица Voyage для asymmetric retrieval содержит следующий средний
результат по 53 наборам:

| Режим | Средний результат |
|---|---:|
| `voyage-3.5-lite` | 75.15% |
| `voyage-4-nano` | 76.41% |
| `voyage-4-lite` | 77.19% |
| `voyage-4` | 79.60% |
| `voyage-4-lite` query + `voyage-4-large` documents | 78.27% |
| `voyage-4` query + `voyage-4-large` documents | 79.91% |

`voyage-4-lite` получает примерно 97% среднего балла `voyage-4` за треть его
цены. Индексация документов моделью `voyage-4-large` и запросы через Lite дают
ещё `+1.08` абсолютного пункта относительно Lite/Lite, сохраняя минимальную
цену каждого пользовательского запроса. Звёздочкой в исходной таблице Voyage
обозначает именно режим с документами, заранее встроенными через
`voyage-4-large`.

Ограничения этих чисел:

- это собственная оценка производителя;
- в опубликованной collapsed-таблице нет строки BGE-M3;
- в ней нет отдельного результата по русскому языку;
- её нельзя численно смешивать с MIRACL, MKQA, RusBEIR или нашим тестом 1С.

Следовательно, утверждать, что Voyage уже доказанно лучше BGE-M3 на нашей книге,
нельзя. Источник: официальная [evaluation spreadsheet](https://docs.google.com/spreadsheets/d/1d-06Fh_LqAGBEEIbHN95OxccXcMWYq5uJ0e9LFKaPI8),
на которую ссылается карточка `voyage-4-nano`.

### Multilingual и русский

Voyage обозначает `voyage-4-large` и `voyage-4` как general-purpose multilingual
retrieval модели, а всю серию 4 — как единое совместимое пространство. Однако
в проверенных первичных источниках нет отдельной цифры для русского языка и нет
исчерпывающего списка языков. Поэтому для русской документации поддержка
multilingual подтверждена качественно, а ожидаемый выигрыш над BGE-M3 — только
гипотеза до нашего теста.

Для сравнения, BGE-M3 имеет опубликованные русские результаты: MIRACL Russian
`nDCG@10 70.1` в dense-режиме и MKQA Russian `Recall@100 76.2`. Эти числа
относятся к другим наборам и не доказывают превосходство над Voyage. Источник:
[официальная работа BGE-M3](https://arxiv.org/html/2402.03216v5).

## Стоимость для нашего корпуса

Расчёт для 6,1 млн входных токенов:

| Модель | Обычный endpoint | Batch API со скидкой 33% | Сейчас при доступном free tier |
|---|---:|---:|---:|
| DeepInfra BGE-M3 | $0.061 | не учитывался | $0.061 |
| `voyage-4-lite` | $0.122 | около $0.0817 | $0 |
| `voyage-4` | $0.366 | около $0.2452 | $0 |
| `voyage-4-large` | $0.732 | около $0.4904 | $0 |

Free tokens не применяются к Batch API. Поэтому пока не исчерпан обычный
200M free tier, стандартный endpoint дешевле batch. 200M токенов — это
приблизительно 32 полные индексации корпуса такого размера, если считать весь
embedding free pool доступным этому проекту. Фактический остаток нужно смотреть
в кабинете Voyage.

После free tier Lite вдвое дороже BGE-M3, но абсолютная разница одной полной
индексации составляет всего `$0.061`. Даже `voyage-4-large` стоит меньше доллара
за полную индексацию текущего корпуса.

### Цена запросов

Для поискового запроса из 50 токенов, без учёта возможного служебного prompt:

| Модель | Один запрос | 1 000 запросов |
|---|---:|---:|
| BGE-M3 | $0.0000005 | $0.0005 |
| `voyage-4-lite` | $0.000001 | $0.001 |
| `voyage-4` | $0.000003 | $0.003 |

## API и совместимость с Grounded Docs

Voyage предоставляет `POST https://api.voyageai.com/v1/embeddings` с Bearer
авторизацией. Минимальный request — OpenAI-подобный объект `{input, model}`;
response содержит `object=list`, `data[].embedding`, `data[].index`, `model` и
`usage.total_tokens`. Это соответствует форме, которую читает используемый в
проекте LangChain `OpenAIEmbeddings`.

Текущий Grounded:

- позволяет задать произвольный `OPENAI_API_BASE`;
- отправляет `model` и `input`;
- не отправляет Voyage-поля `input_type`, `output_dimension`, `output_dtype` и
  `truncation`;
- используемый OpenAI SDK автоматически запрашивает `encoding_format=base64`,
  а затем декодирует ответ в float-массив;
- разбивает индексацию по 100 текстов и примерно 50 000 символов, что заметно
  ниже лимитов Voyage;
- хранит float-векторы в `sqlite-vec` и уже рассчитан на размерность 1024.

Поэтому вариант без кода технически совместим:

```dotenv
OPENAI_API_BASE=https://api.voyageai.com/v1
DOCS_MCP_EMBEDDING_MODEL=openai:voyage-4-lite
DOCS_MCP_EMBEDDINGS_VECTOR_DIMENSION=1024
```

В секретное значение `OPENAI_API_KEY` при таком smoke-тесте передаётся ключ
Voyage. Это не предложение менять production сейчас, а только описание
совместимого контракта.

9 августа 2026 года контракт дополнительно проверен живыми запросами именно с
удалённого сервера. `voyage-4-lite`, `voyage-4` и `voyage-4-large` вернули HTTP
200, нормированные float-векторы длины 1024. Запрос без `input_type` принят.
OpenAI-форма с `encoding_format=base64` также принята, поэтому транспортная
совместимость с текущим SDK подтверждена. Один короткий запрос занимал примерно
0,42 секунды; три последовательных вызова query/document — около 1,3 секунды
для каждой модели. Это проверка API, а не оценка retrieval-качества.

### Почему всё же нужен маленький adapter

Voyage настоятельно рекомендует retrieval-клиентам не оставлять `input_type`
пустым:

- документы: `input_type=document`;
- запросы: `input_type=query`.

На backend к текстам добавляются разные retrieval-prompts. Текущий
`OpenAIEmbeddings` не передаёт поле `input_type` и одинаково вызывает endpoint
для `embedDocuments()` и `embedQuery()`. Поэтому no-code режим теряет важную
часть рекомендованного поведения модели.

Минимальный adapter должен:

1. реализовать имеющийся интерфейс LangChain `Embeddings`;
2. для `embedDocuments()` отправлять `input_type=document`;
3. для `embedQuery()` отправлять `input_type=query`;
4. использовать `output_dimension=1024`, `output_dtype=float`,
   `truncation=false`;
5. поддерживать отдельно `documentModel` и `queryModel`, если тестируется
   комбинация Large/Lite;
6. проверять размерность и норму ответа.

Это не требует менять SQLite, поиск или формат chunks. Понадобятся новый
provider, настройки и полная переиндексация.

Официальный контракт и input types: [Voyage embeddings API](https://docs.voyageai.com/reference/embeddings-api),
[FAQ](https://docs.voyageai.com/docs/faq#when-and-how-should-i-use-the-input_type-parameter).

## Нормализация, Matryoshka и усечение

- Voyage сообщает, что его embeddings нормализованы до длины 1. Поэтому
  dot-product, cosine и Euclidean дают одинаковый порядок. Текущий поиск через
  L2 в `sqlite-vec` подходит.
- Серия 4 поддерживает Matryoshka-размерности 256, 512, 1024 и 2048. Первые
  `k` координат полного вектора образуют корректный более короткий embedding;
  после ручного усечения его нужно снова нормализовать.
- API-параметр `output_dimension` сразу возвращает нужную размерность. Для
  первого сравнения лучше оставить 1024: это совпадает с BGE-M3 и исключает
  размерность как дополнительную переменную.
- `truncation` по умолчанию равен `true`. Для controlled ingestion разумнее
  задать `false`, чтобы слишком длинный chunk завершался явной ошибкой, а не
  незаметно обрезался.
- Серия 4 умеет `float`, `int8`, `uint8`, `binary`, `ubinary`. Текущий
  `sqlite-vec` индекс настроен на `FLOAT[N]`, поэтому без более глубокой
  доработки нужно оставить `float`.

Источники: [FAQ о нормализации](https://docs.voyageai.com/docs/faq#which-similarity-function-should-i-use),
[flexible dimensions and quantization](https://docs.voyageai.com/docs/flexible-dimensions-and-quantization),
[API reference](https://docs.voyageai.com/reference/embeddings-api).

После добавления платёжного метода Tier 1 даёт:

| Модель | TPM | RPM |
|---|---:|---:|
| `voyage-4-lite` | 16M | 2 000 |
| `voyage-4` | 8M | 2 000 |

На один request разрешено до 1 000 текстов. Общий токенный лимит request:

## Рекомендуемый эксперимент

Не переключать production сразу. Провести тест так:

1. Сохранить текущие BGE-M3 результаты 40 qrels как baseline:
   `MRR 0.684`, `nDCG@5 0.712`, `Recall@3 0.688`, `Hit@1 0.575`.
2. В отдельной копии индекса полностью переиндексировать тестовую библиотеку
   через `voyage-4-lite`, 1024 float, с правильными `input_type`.
3. Прогнать те же 40 вопросов сначала без reranker, чтобы измерить именно
   candidate retrieval.
4. Затем применить уже выбранный `rerank-2.5-lite`, чтобы проверить итоговую
   систему.
5. Только если Lite не даёт нужного качества, проверить asymmetric-вариант:
   `voyage-4-large` для документов + `voyage-4-lite` для запросов.

Критерий решения — не публичный средний benchmark, а выигрыш Recall@30 и
Recall@3 на наших qrels. Reranker не сможет исправить ответ, если релевантный
chunk вообще не попал в candidate set.

## Итоговая рекомендация

- **Самый разумный первый кандидат:** `voyage-4-lite`, 1024 float.
- **Без доработок:** годится для smoke/предварительного теста, но не использует
  `input_type` и потому не должен становиться окончательной конфигурацией.
- **С небольшим adapter:** Lite/Lite с правильными input types; затем при
  необходимости Large-documents/Lite-queries.
- **Не выбирать сейчас:** `voyage-4` и `voyage-4-large` как единственную модель
  для каждого запроса — цена выше, а embeddings запросов не являются узким
  местом и всё равно требуется локальная проверка качества.
- **Не отказываться заранее от BGE-M3:** после добавления Voyage reranker уже
  достигнуты `MRR 0.933` и `nDCG@5 0.937`. Возможно, замена embeddings даст
  небольшой дополнительный выигрыш и окажется менее приоритетной, чем штатная
  реализация reranking.
