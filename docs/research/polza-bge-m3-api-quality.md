# BGE-M3 через Polza: почему semantic retrieval мог стать хуже

Проверено 2026-08-09 по первичным источникам.

## Краткий вывод

Снижение semantic-метрик не выглядит признаком того, что Polza возвращает
«урезанный» или неправильный BGE-M3. Polza заявляет для `baai/bge-m3`
1024-мерный **dense vector** и отдаёт его через стандартный OpenAI-совместимый
`POST /embeddings`. Именно такой единственный вектор умеет принимать текущий
Grounded Docs.

BGE-M3 раскрывает полные возможности при сочетании трёх выходов: dense,
sparse/lexical и multi-vector ColBERT. Официальная карточка модели рекомендует
hybrid retrieval и reranking. Стандартный ответ Polza `/embeddings` содержит
только поле `embedding`; параметров для возврата sparse weights или ColBERT
vectors в опубликованной схеме нет. Но даже если получать эти выходы напрямую,
Grounded Docs без доработки всё равно не сможет их сохранить и применить.

Поэтому фактически сравнивались:

- OpenAI `text-embedding-3-large` как dense-модель;
- только dense-режим BGE-M3, без его sparse и ColBERT частей.

Это наиболее вероятное объяснение результата. BGE-M3 не обязана превосходить
OpenAI Large именно в dense-only semantic search на конкретной русской книге.

## Что именно доступно через Polza

Страница модели Polza описывает BGE-M3 как модель, кодирующую текст в
1024-мерное dense-пространство. Страница API документирует OpenAI-совместимый
ответ вида `data[].embedding` и не документирует выходы `lexical_weights` или
`colbert_vecs`. На странице модели также указан фактический backend
`deepinfra/fp32`.

Вывод: через опубликованный интерфейс Polza доступен dense-вектор BGE-M3.
Sparse и ColBERT через этот API не подтверждены и стандартной схемой не
предусмотрены.

## Instruction и нормализация

- **Query instruction не требуется.** Официальная карточка BGE-M3 прямо
  отмечает, что модель больше не требует добавлять instruction к запросам.
- **Dense-векторы следует L2-нормализовать.** Официальная реализация
  `FlagEmbedding` включает `normalize_embeddings=True` по умолчанию и применяет
  `torch.nn.functional.normalize` к dense embedding. Если и документы, и
  запросы в нашем индексе нормализованы, это не объясняет ухудшение. Если
  нормализована лишь одна сторона либо ни одна при L2-поиске, ранжирование может
  отличаться от эталонного cosine/dot-product режима.

## Может ли проблема быть на стороне провайдера

Теоретически — да: агрегатор может использовать иную serving-реализацию,
пулинг или нормализацию. Но опубликованные данные не дают оснований утверждать,
что Polza возвращает неправильную модель: идентификатор, размерность 1024 и
описание dense-выхода согласуются с BGE-M3. Отсутствие sparse/ColBERT — это
ограничение стандартного embeddings API, но для нынешнего Grounded Docs оно не
меняет результат, потому что сервер всё равно работает dense-only.

Для проверки провайдера без догадок нужен паритетный тест: одинаковые строки
прогнать через Polza и официальный `BAAI/bge-m3`/FlagEmbedding, затем сравнить
cosine similarity соответствующих векторов и итоговое ранжирование. Совпадение
самих координат не обязательно из-за разных версий serving, но матрица
попарных similarity должна быть близкой.

## Практический итог для нашего теста

1. Не добавлять query instruction.
2. Проверить L2-норму векторов документов и запросов непосредственно в
   работающем поисковом тракте; обе стороны должны обрабатываться одинаково.
3. Не считать небольшой результат на semantic-подмножестве доказательством
   дефекта API: это отдельная dense-модель и ограниченная тестовая выборка.
4. Чтобы использовать преимущество BGE-M3 полностью, потребуются sparse/ColBERT
   индексы и объединение оценок — то есть доработка Grounded Docs. Простая смена
   OpenAI-compatible endpoint этого не включает.
