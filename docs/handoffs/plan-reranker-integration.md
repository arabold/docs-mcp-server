# Handoff: спланировать reranking в Grounded Docs

## Задача нового чата

Подготовить проверенный по коду план добавления необязательного этапа reranking
в `docs-mcp-server`. В этом чате требуется план, а не реализация.

Рабочая директория:

`/home/as/ai-projects/docs-mcp-server`

1. `README.md`;

## Проверенный результат

Внешний тест выполнен на удалённом production-сервере без изменения Grounded и
без переиндексации:

`BGE-M3 dense + FTS5/RRF top-30 -> Qwen3-Reranker-8B -> новый порядок`

На прежнем наборе из 40 вопросов по `ONEC_ERP_IMPLEMENTATION`:

- MRR: `0.684 -> 0.917`;
- nDCG@5: `0.712 -> 0.923`;
- Hit@1: `0.575 -> 0.875`;
- Recall@3: `0.688 -> 0.975`;
- улучшились 14 вопросов, не изменились 23, ухудшились 3;
- 39 из 40 эталонов находились в top-30;
- все 40 API-вызовов завершились успешно.

После этого тот же тест выполнен на Voyage `rerank-2.5-lite`:

- MRR: `0.933`;
- nDCG@5: `0.937`;
- Hit@1: `0.900`;
- Recall@3: `0.975`;
- средняя задержка: `1.11 с`, P95 `1.26 с`;
- 17 улучшений, 2 ухудшения, 21 без изменений;
- использовано 1 816 288 токенов, стоимость в текущем free tier — `$0`.

Этот размеченный набор проверяет `ONEC_ERP_IMPLEMENTATION`. Пяти-вопросный пилот
на большой библиотеке `ONEC_ERP` тоже показал улучшение, но не заменяет
отдельный полный набор qrels для основной книги.

Полные условия, ошибки и стоимость находятся в отчёте
`docs/research/qwen3-reranker-onec-full-eval.md`. Использовать его как
единственный источник чисел, не восстанавливать результаты по памяти.

## Целевая архитектура

Сохранить текущий candidate retrieval и добавить один поздний этап:

`DocumentStore hybrid retrieval -> RRF candidates -> reranker -> context assembly`

Reranker должен получать короткие исходные chunks. Внешний пилот передавал уже
собранные результаты `search_docs`, поэтому его задержка и стоимость являются
верхней оценкой, а не производственным бюджетом.

Первый провайдер: Voyage `rerank-2.5-lite`. Проектировать общий интерфейс, чтобы
провайдера можно было заменить. DeepInfra Qwen 0.6B оставить возможным дешёвым
fallback после бесплатного периода Voyage.

## Обязательные свойства плана

План должен определить по фактическому коду:

1. Точную точку вставки reranker между RRF и сборкой контекста.
2. Контракт общего `Reranker`: query, candidates, scores/order, metadata.
3. Voyage-клиент и контракт `/v1/rerank`: `model`, `query`, `documents`,
   `top_k`, `truncation`; отдельно предусмотреть расширяемость для DeepInfra.
4. Конфигурацию:
   - выключено по умолчанию;
   - provider/model/base URL;
   - `VOYAGE_API_KEY` без сохранения значения в конфигурации;
   - candidate limit, по умолчанию 30;
   - timeout, retry, service tier;
   - instruction и возможные overrides по библиотекам.
5. Fail-open: при любой ошибке возвращается исходный порядок RRF.
6. Поведение score, tie-break, дедупликации URL и итогового `limit`.
7. Ограничение размера каждого chunk и общего числа токенов запроса.
8. Безопасную телеметрию без текста запросов, документов и токенов доступа.
9. Unit, integration и E2E тесты по правилам репозитория.
10. Повторный 40-вопросный benchmark после реализации.
11. Документацию конфигурации и deployment-переменных.
12. Миграцию без повторной индексации существующих библиотек.

## Границы первого релиза

В первый релиз входят только текущий RRF candidate retrieval и внешний
reranker. BGE-M3 learned sparse, ColBERT multivectors, Qdrant, Vespa и смена
embedding-модели остаются отдельными будущими экспериментами.

Существующее поведение при выключенном reranker должно остаться идентичным.
Существующий production-сервер не переключать во время планирования.

## Критерии готовности плана

План готов, когда:

- каждая затрагиваемая точка названа реальным файлом, классом и методом;
- для каждого шага есть проверяемый результат;
- отдельно описаны happy path, timeout, 4xx/5xx, rate limit и недоступность
  провайдера;
- указан порядок red-green тестов и команды Node.js 22 для проверки;
- качество после реализации проверяется теми же 40 qrels;
- целевой ориентир не ниже `MRR 0.90` и `nDCG@5 0.90` при нуле ошибок;
- план не требует переиндексации и не включает несвязанный рефакторинг.
